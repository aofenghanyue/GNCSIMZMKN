# License status

No general repository distribution license has been selected. This notice is not an additional license grant.

On 2026-08-15, the repository owner accepted a public-GitHub-collaboration G1 scope for work with `zbyandmoon` and directed that the origin remain public. The origin and the existing fork `zbyandmoon/GNCSIMZMKN` were confirmed public on the same date. GitHub's Terms of Service grant platform-scoped rights for public content, including viewing and forking through GitHub functionality. Those platform rights do not establish a general open-source or outbound distribution license. See [GitHub's repository licensing guidance](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository) and [GitHub Terms of Service §D](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service#d-user-generated-content).

Current implementation, local validation, issues, reviews, forks, and pull requests may be used for the accepted GitHub collaboration scope. The implementation agent may create local commits and will not push, merge, tag, publish a release, send a separate public bundle, or change remote settings without explicit user authority.

General outbound distribution remains blocked for repository content, imported architecture blueprints, fixtures, oracles, benchmarks, reports, and binaries. In this policy, general outbound distribution means release assets, source or binary bundles, datasets, report attachments, Legacy archives, and delivery channels outside the accepted public GitHub collaboration. The frozen Legacy reference remains read-only, evidence-only, and excluded from any separate distribution candidate until ownership and license evidence are resolved. Its presence in the public repository is an owner-accepted exposure fact and does not establish rights clearance.

Eigen, w64devkit, host toolchains, Python, PowerShell, CMake, and CI actions are executed outside the repository and are not bundled in the current project. Any future vendoring, runtime bundling, container, installer, or binary release requires a review of the exact delivered components and their upstream terms.

The current boundary and executable check are documented in [ADR-0008](docs/adr/0008-internal-default-license-and-provenance-gate.md) and the [license and provenance policy](docs/governance/license-and-provenance-policy.md). Third-party contributions require a rights check before they are merged into a future licensed or released artifact; no CLA, DCO, or receipt mechanism is introduced for the current collaboration slice.

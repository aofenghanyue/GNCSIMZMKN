## 1. 结论摘要

这套蓝图在**结构层**是罕见的体系化设计：15 册共享一条主线（意图→编译→计划→执行→提交→证据）、零断链、每册声明主线定位，01 现状审计经逐条代码验证全部属实，14/15 册给出了可执行的 step 时间线和组件级落位。**它不是概念拼接。**

但"词典拼接"的观感是真实的，其来源有三，按严重程度排序：

1. **术语体系失控**（最严重）：约 200 个自造术语只有 42 条叙事层词表，同一概念多个名字、同一个词多个含义、两册之间互斥的枚举尚未仲裁。这是阅读障碍和未来实现歧义的第一来源。
2. **当前层次是"规范"而非"设计"**：每册都精确到字段表、枚举和规则，却没有任何一个完整实例，也没有决策链和承诺闭合。设计不是"写代码"，而是让规范**可判定**——现在做不到。
3. **内容风格割裂**：00/README/02 有叙事有例子，03 起退化为"必须/禁止/默认 + 字段表"，读者无法从任何一册独立建立心智模型。

委托方已接受的取舍（实现成本、不写代码、宁可过度设计）不在本评审的问题列表内；但过度设计有一个**衍生成本**必须治理：词汇越庞大，一致性负担越高——术语仲裁因此从"文档洁癖"升级为"架构可行性的前置条件"。

## 2. 评审方法与可信度

本评审的可信度建立在两个实证动作上：

1. **源码验证**：01 册的全部 14 项现状声称逐条回到代码核实，**14 项全部属实**，包括最容易编造的细节：
   - `ForceMomentInteraction6Dof::computeYyzC6Input(...) const` 内的 `mutable last_input_`（const 查询写缓存，RK stage 数量改变被观测结果）；
   - `ConfigManager::loadFromFile` 解析/预处理失败路径不清空旧 `config_`（调用方忽略 false 会读取过期内容）；
   - `rate_hz` 必须形成整数仿真步长（否则抛错）；
   - CMake 以宏文本扫描发现项目组件；
   - `Simulator` 的 11 项职责、两套积分语义、三套姿态表示并存等全部命中。
   
   结论：01 册是**基于真实代码的证据**，不是虚构审计。这是整套蓝图的信任基石，值得肯定。

2. **并行细读**：03–15 各分册由独立代理通读并交叉比对（术语使用、悬空名词、与 02 主线的一致性），发现的不一致条目均附行号，见附录。

## 3. 正面评价

### 3.1 主线叙事是完整的设计，不是名词堆

- 02 册的四类 AuthorityDomain、三道防火墙、A–F 变化分流，是**有推导链**的架构决策，不是分类学陈列；
- 06 册给出 21 状态 Session 状态机和四类 commit 边界（ModelCommit / ObservationSeal / ExternalEffectCommit / EvidenceCommit），明确了"模型事实"与"文件持久化"的原子性差异；
- 14 册给出了**唯一可执行的 step 时间线**（publish → boundary DAG → stage → validate → commit → seal，含 terminal/continue/rollback/cancel 全分支），与 02 的算子序列逐一对位——这是整套设计中可判定性最高的部分；
- 15 册把抽象落到真实组件：YYZ 目标运行图（RigidBody6Dof/ImuSensor/GuidanceLoop…）、100/50/10 Hz 周期表、`GuidanceProcess` 逐成员搬迁表、CAVH Eq17/Eq18 的 kernel 分层——这是"工程落位"级，不是散文。

### 3.2 治理体系体现了罕见的纪律

- 删除台账（legacy → target → 删除门）明确到 `SimulationNode`、`NodeFactory`、`IObservable` 等具体对象；
- 三层 fitness functions（FF-ARCH/FF-DEP/FF-OBJ…）把架构规则变成可自动检查的断言；
- 科学 oracle 分层（数学性质→数值算法→模型 kernel→组件契约→closure→纵向 mission）给出了"重写如何不丢科学参照"的完整方法；
- "旧结果能跑"与"曲线看起来接近"都不构成接受理由——这种标准在自研框架文档中极其少见。

### 3.3 架构思想本身是正确的

编译前置（Plan Firewall）、状态所有权唯一、事务提交、证据谱系、格式中性（Source Frontend / Dataset Sink 把 JSON/CSV/INI 踢到链路两端）、AuthorityDomain 作为变化管理工具——对研究仿真框架都是正确方向，且与现状审计发现的既有优点（发布态语义、同步提交、显式连续组、SimFlow 外置）一脉相承，不是推倒重来而是补全。

### 3.4 文档治理规则的自我约束有效

README 的"三个嵌套尺度""六次权威交接""每册必须声明主线定位"等规则执行得相当彻底：所有分册开头都有主线定位声明，无断链，术语表独立放置。**结构层的问题不是体系缺失，而是词汇与实例层没有执行同样的治理。**

## 4. 核心问题一：术语体系失控（最严重）

### 4.1 事实

逐册统计（与 42 条词表对照），正文实际使用的规范层术语约 200 个，其中约 100 个在词表中完全缺席，包括高频运行期核心词：`RunOutcome`、`NumericalOutcome`、`StepTransaction`、`state_epoch`、`ObservationBatch`、`DiagnosticRecord`、`waiver`、`Quality`、`StateFragment`、`PreparedModel`、`criticality`、`lineage`。词表收录的却是 AuthorityDomain、CapabilitySlice、ChangeVector 这类**叙事层分析词汇**——"统一术语表"实际是"02 词汇表"。

### 4.2 同义异名（同一概念，多个名字）

| 概念 | 现存名字 | 分布 |
| --- | --- | --- |
| 连续积分组合体 | `IContinuousGroup` / `IntegrationScope` / `ContinuousClosureGroup` / `Solver Island` | 03 §15.5 / 04 §7.2、06、14 / 14 §14 / 02 §5.2、05、15 |
| 组件组合描述 | `Component Recipe` / `RuntimeCellRecipe` | 13 §3 标题 / 12 混用、glossary |
| 诊断记录 | `StepDiagnostic` / `DiagnosticRecord` / `Diagnostic` | 03 L91 / 04、07 / glossary |
| 渲染后的诊断 | `RenderedDiagnosticSnapshot` / `RenderedDiagnostic` | 07 §4.1 / 07 §10.6 |
| 持久化诊断集合 | "diagnostic bundle" / `DiagnosticBatch` / `diagnostic-bundle` | 07 L59、L97 / 07 §10.5 / 08 L289 |
| 端口绑定计划 | `PortBindingPlan` / `Binding Plan` | 04 §1 L13 / 04 §8 整节 |
| 观测草稿 | `ObservationDraft` / "ObservationBatch draft" | 08 §6 图 / 08 A0 |
| 观测投影计划 | `ObservationProjectionPlan` / `ObservationPlan` | 08 §3.3 / 08 §5（两者关系从未建立） |
| kernel 结果层 delta | `InstantStateEffect` / `IntervalStateEffect` | 12 L162（一次）与全书的 `InstantPatch` / `IntervalCandidate` 未桥接 |

### 4.3 一词多义（同一个词，多个含义）

- `authority`：导航源主导权（09 §13.1、10 §6.3）/ 权威域（02 全册）/ 命令权限（10 §21.2）——三义混用；
- `profile`：训练/评估 profile（10 §11.4）/ 保真度 profile（10 §19）/ 组件组合 profile（02 §5.1）——三义无关；
- `capability`：基于能力的权限（10 §21.2）/ Kernel 扩展准入门（02 §9.2）——一权限一内核；
- `MissionPatch`（10 册，LLM 提案类型）vs `CompilePatch`（02/09，case 物化类型）——近名异义，两册互不引用；
- "Closure"一词五义：execution form（ClosureDescriptor）、连接类型（ContinuousClosureLink）、闭合策略（三种 Closure）、闭合对象（ContinuousClosureGroup）、证据（closure proof）——文中均不消歧。

### 4.4 跨册互斥（两册各自为政且互相矛盾）

- **criticality 分级**：07 §15.2 四级（CriticalEvidence / RequiredOperational / BestEffortDisplay / DebugOnly，sink/field 级）；08 §5.3 五级（把 RequiredOperational 拆成 RequiredMetricInput / OperationalTelemetry，field 级）——粒度、归属对象均不同；
- **validity 词族六种表达**：07 枚举 Valid/ValidWithCaveats/Invalid/Unknown；07 文本用枚举外的 "Invalidated"（L642）；08 ObservationBatch 用 valid/partial/invalid；08 ArtifactDescriptor 用 valid/caveated/invalid/partial；08 文本用 "incomplete"；02 §1.4 用 "Invalidated/Incomplete"——partial 只在 08、Unknown 只在 07、incomplete 无枚举归属，词表无仲裁条目；
- **PreparedModel 缓存 key**：05 L508（definition、asset、policy hash）vs 06 L168（ModelDefinition/version、occurrence config hash、asset hash、implementation version、numerical policy）——字段集不同。

### 4.5 影响

- **阅读**：读者无法区分"新概念"与"旧概念的新名字"，每页都要自行建对照表——这是"词典拼接"观感的直接来源；
- **实现**：两册同时开工必然产生同义重复实现；枚举互斥会导致接口错配（例如 07 与 08 对 criticality 的理解不同，编码器与 sink 无法对上）；
- **未来演进**：这套词汇是前置承诺——一旦对象按错误的名字建成，改名成本高于设计期仲裁成本。

## 5. 核心问题二：当前层次是"规范"而非"设计"

委托方声明"不需要写到具体代码层次"——接受。但问题不在于"没写代码"，而在于**规范不可判定**：

- 规范回答"系统有哪些概念、长什么样"（字段表、枚举、规则）；
- 设计回答"为什么这样、怎么用、能不能闭环"（决策链、实例、承诺闭合）。

当前 15 册几乎全部停留在第一层。具体表现：

### 5.1 有形状、无实例

没有任何一册给出一个**完整实例**（数据级即可，不需要代码）：

- 07 册规定了 18 个诊断 namespace、code 格式 `GNC-<DOMAIN>-<NNNN>`，全册唯一的 code 实例是 `GNC-CFG-xxxx`（占位符，L560）；没有一条真实 code 条目、没有 waiver 实例、没有 policy rule 实例；
- 05 册规定了 12-pass 编译管线和 Descriptor 的全部内容清单，没有任何一份 Mission IR JSON 或 Descriptor 字段级示例；
- 08 册给了 Run Bundle 目录树和 epoch 对写法，没有一条 ObservationBatch / Run Manifest 的 JSON 样例；
- 09 册规定了 TaskDefinition 14 字段区域和九部件 Tool Adapter，没有一份 TaskDefinition YAML、没有任务与部件的对应实例；
- 10 册给了 Python 对象面（Workspace/Catalog/Compiler/Session…），**一个 API 签名都没有**，LLM Proposal 九字段无 schema 示例；
- 15 册是唯一例外——它有 YYZ/CAVH 的完整落位实例，因此也是整套文档中最接近"设计"的一册。

**字段表定义的是"可能的形状"，实例定义的才是"这套形状组合起来确实可行"**。一个真实的 Diagnostic code 条目、一段 YYZ mission 的 Mission IR JSON、一份带实际值的 Descriptor 表——这些不需要一行 C++，但能让整册规范从"目录"变成"设计"。

### 5.2 承诺不闭合

多处"声称的机制"只有名字没有内容：

- **closure proof 体系（最严重）**：02 定义七类 closure、05 反复点名 proof records / proof index / `--explain`（05 L54、L428、L479、L536、完成定义 13），路线图 R0.7 要求"plan-as-proof-artifact"——但**没有任何一册给出 proof 记录的结构、验证方法或运行期消费方式**。这是全链唯一只有名字没有内容的环节；
- 09 册 adapter 九部件与 DATCOM/GPOPS2 任务步骤两套分类平行存在，**没有任何一处说明"此任务由哪个部件实现"**；Operation 六算子（Admit/Authorize/Reserve/…）与 §4 任务状态机也无映射声明；
- 08 册 lineage edge 给了 role 枚举（6 种）和 provenance 来源（4 类），**没有 edge 的数据结构、写入者、写入时机和存储位置**；
- 10 册 §14.1 六子层（Event Hub/Policy Engine/Audit Store）、§21 安全模型九项控制，列完即止，与建设顺序 X0–X6 完全脱节；
- 03 册声称的"回路裕度、频域分析"（M6 层）正文零展开；`StepDiagnostic`（L91）、`RootProblem`（L514）、`ObservationPolicy`（L499）各出现一次即消失。

### 5.3 决策链不完整

- 每册有"目标决策"标记，但多数决策**没有给出证据链**——它解决的是 01 审计中的哪个问题、替代哪个现状行为、与 02 哪条主线交接。15 册做了这个工作（目标对象→源码文件→成员搬迁表），03–10 大部分没有；
- 各册"完成定义"（如"所有公开失败都映射到稳定 Diagnostic code"）的验收项与当前内容的空白之间存在整条时间差，文档未标注"该验收依赖尚未落地的哪些实例"。

### 5.4 建议的判定标准

一份分册从"规范"升级为"设计"，应满足四条：

1. **实例闭合**：每个核心对象至少有一个数据级实例（真实值，非占位）；
2. **决策可追溯**：每个"目标决策"能指出其解决的现状问题（引用 01 审计编号或源码证据）与下游消费者；
3. **承诺闭合**：被点名两次以上的机制（proof、lineage edge、adapter 部件、policy 落点）必须有结构定义或显式标注"延后，见 R 阶段"；
4. **跨册无冲突**：共享概念（criticality、validity、cache key、closure 家族）在词表中仲裁并全库统一。

## 6. 核心问题三：内容风格割裂

### 6.1 事实

- **有叙事的一侧**：00（愿景与宪章）、README（三个尺度、六次交接、阅读路线）、02（主叙事 A–J 走查，含"舵机卡死→坠毁"因果链、DATCOM 纵向走查）——这一侧有例子、有推导、可独立阅读；
- **规格的一侧**：03–13 几乎全部退化为同一句式（"必须/禁止/默认 + 名词表"），每节结尾挂一张字段表。没有一个分册像 `doc/00-current-architecture.md` 那样用"一次仿真怎样从配置走到结果"的口吻开场；
- **互链不对称**：07 是唯一不回引 02 的分册（代理已确认）；08 对路线图 R3 的引用无链接；
- **mermaid 图与正文脱节**：多册图中出现孤儿节点（08 的 Memory/RL Sink、ObservationDraft；09 的 "Workflow Outcome" 与正文 "WorkflowOutcome"），图与正文无对应表。

### 6.2 后果

读者必须先读完 02 并内化整套词汇，才能进入任何一册；任何一册单独拿出来都无法自举。对一份"将被反复查阅"的设计文档集，这个门槛过高——尤其当实现周期拉长时，每册都应是"可独立取用"的参考。

### 6.3 建议方向

- **补一本《第一册》**（5–8 页）：用"从 YYZ mission.json 到一行 CSV 再到一条诊断"的完整故事，只用 20 个核心概念讲一遍主线——给未来的读者一个不用先背词表的入口；
- **每册开头加一个"本册一口气读完"的实例**：一个真实的 Diagnostic code、一段 Mission IR JSON、一条 epoch 对——规格之前先给形状；
- **统一 mermaid 命名**：图节点名与正文类名必须一一对应，禁止图内新名；
- **补齐 07→02 回链**。

## 7. 对架构设计的独立判断

委托方已声明：宁可过度设计，也不留未来重构风险。此取舍被接受，不再作为问题列出。但过度设计有一个**衍生成本**必须在设计中治理：

**词汇规模与一致性负担成正比。** 扩展机制（九类接缝、AuthorityDomain、CapabilitySlice）的价值在于"未来需求能落到预定位置"；但如果落位时找不到唯一的词（第 4 节问题），机制本身就无法执行——**术语仲裁是这套扩展机制可行性的前置条件**，而不是文档洁癖。

两点具体判断：

1. **核心语义层（编译器/事务内核/证据链）设计质量高，值得全量投入**。step 事务模型、Plan Firewall、状态所有权唯一——这些是"最终好用"的骨架，本评审无异议。
2. **元层装置（七维 ChangeVector、closure proof、每需求 CapabilitySlice 分解）的使用策略建议分级**：不是砍掉，而是限定"何时必须全套走"——F 类（Kernel/原子性/权威域语义变化）必须全套；A/B/C/D/E 类（新算法、局部行为、新连接、新工具、新前端）走简化检查。否则装置本身的流程成本会成为未来每个普通需求的常数开销。02 册自己说"七维来自语义主干上七个不可互相代答的问题"——它作为**评审坐标**是对的，作为**每个需求的强制工作流**则过重。

## 8. 改进建议（按优先级）

### P0 — 术语治理（先于一切修订）

1. **补全词表**：把附录列出的约 100 个规范层术语全部补入 glossary，每条含"唯一名 + 定义 + 权威分册"；词表从"02 词汇表"升级为"全库注册表"。
2. **裁决同义集群**：Solver Island / IntegrationScope / ContinuousClosureGroup 留一个（建议保留一个并让其余成为其别称条目）；Component Recipe / RuntimeCellRecipe 留一个；validity 词族统一成一个枚举并在 02/07/08 三册引用同一处定义；criticality 统一为一级并在 07/08 对齐；PreparedModel cache key 两册对齐。

## 10. 评审结论

这套蓝图**值得按当前方向继续投资**：主线叙事成立、现状审计可信、step 语义可执行、治理体系有纪律。三项核心问题中，**问题一（术语）是阻塞性的**——它不修，问题二和问题三的修订都会在错误的词汇上叠加；**问题二（规范→设计）是决定这套蓝图最终是"好设计"还是"好目录"的关键**；**问题三（风格）是读者体验的直接成本**。

建议修订顺序：P0 术语治理 → P1 实例与承诺闭合 → P2 可读性与使用策略。全部完成后，这套文档将达到"架构蓝图"应有的判定性：任何一个新需求都能在词表注册后落到唯一接缝，任何一个旧对象都能在删除台账中查到去向，任何一个概念都能从实例直接推演到实现。

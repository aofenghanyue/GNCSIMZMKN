## 1. 总体判断

专家对主线、现状审计、step 事务和纵向落位的肯定有充分文本与源码证据。三项核心批评也成立：共享词汇缺少统一注册；若干关键机制只有承诺名称；03–13 的规格密度远高于实例密度。这些问题会让两个分册在并行实现时产生不同对象、不同枚举和不同验收口径。

本轮接受以下方向：

1. 把 glossary 提升为全库术语注册表，统一名称、状态、别名和权威分册；
2. 仲裁 `EvidenceValidity`、`EvidenceCriticality`、`PreparedModelKey` 等跨册共享定义；
3. 为 Mission 编译、诊断、Observation/Manifest、Workflow Task、LLM Proposal 和 lineage edge 给出数据级参考实例；
4. 给 `PlanProofRecord`、Tool Adapter 映射、Workflow operator 映射和 lineage 写入协议补齐结构与消费链；
5. 增加一份从 YYZ source 到 CSV、Diagnostic 和 Evidence Bundle 的短路径入口；
6. A–E 类普通变化采用简化 Change Card，F 类及跨权威域高风险变化采用完整 CapabilitySlice；
7. 每册在规格前先给一个来自同一参考 fixture 的局部实例。

两项建议采用调整后的实现：

- `IContinuousGroup`、`IntegrationScopePlan`、`SolverIslandPlan` 处在不同阶段。目标文档移除 `ContinuousClosureGroup`，保留“legacy interface → compiled integration scope → optional nested solver island”的转换关系；
- 延期能力仍承担架构压力测试。它们保留在相关分册，但必须进入统一能力状态表，并在标题或表格中标明 `V1`、`PressureOnly` 或 `Deferred`，防止读者误判交付范围。

## 3. 术语仲裁决定

| 问题簇 | 唯一名称或关系 | 被替换或受限的写法 |
| --- | --- | --- |
| 连续积分边界 | `IntegrationScopePlan` 是编译产物；`SolverIslandPlan` 是 scope 内可选联立求解子计划；`IContinuousGroup` 只指当前代码迁移源 | `ContinuousClosureGroup` 从目标词汇退出；裸 `IntegrationScope` 只作口语 |
| 组件组合 | `RuntimeCellRecipe`；正文写作 Runtime Cell Recipe | `Component Recipe` 退出 |
| 端口绑定 | `BindingPlan`；正文写作 Binding Plan | `PortBindingPlan` 退出 |
| 状态变化 | `InstantPatch` 与 `IntervalCandidate` | `InstantStateEffect`、`IntervalStateEffect` 退出 |
| 诊断 | `DiagnosticDraft` → `DiagnosticRecord` → `DiagnosticBatch`；持久化产物为 `DiagnosticBundleArtifact` | `StepDiagnostic` 退出；裸 diagnostic bundle 只允许表示 artifact type `diagnostic-bundle` |
| 诊断渲染 | `RenderedDiagnostic` | `RenderedDiagnosticSnapshot` 退出 |
| 观测 | `ObservationDraft` 经 seal 形成 `ObservationBatch`；`ObservationProjectionPlan` 是 `ObservationPlan` 的已编译投影子计划 | “ObservationBatch draft”退出；两类 Plan 保留父子关系 |
| 有效性 | `EvidenceValidity = Valid \| ValidWithCaveats \| Partial \| Invalid \| Unknown` | `Invalidated`、`Incomplete` 只作 reason/state transition，不作枚举值 |
| 关键度 | `EvidenceCriticality = CriticalEvidence \| RequiredMetricInput \| OperationalTelemetry \| BestEffortDisplay \| DebugOnly` | `RequiredOperational` 退出 |
| PreparedModel 缓存 | `PreparedModelKey` 使用一份字段定义 | 05/06 各自列字段退出 |
| Mission 与 case patch | `MissionSourcePatch` 是 authoring proposal；`CompilePatch` 是已批准并物化到编译输入的 case patch | `MissionPatch` 退出；两者通过 approval/materialization receipt 连接 |
| authority | `AuthorityDomain`、`StateOwner`、`DecisionAuthority`、`PermissionGrant` 分别使用限定名 | 裸 `authority` 不作为跨册类型名 |
| profile | `RuntimeCellProfile`、`RunProfile`、`TrainingProfile`、`FidelityLevel` 分别命名 | 裸 `profile` 只用于自然语言描述 |
| capability | `KernelCapability`、`BackendCapability`；权限使用 `PermissionGrant` | 权限语义中的 capability 退出 |
| Closure | `ClosureDescriptor`、`ContinuousClosureLink`、`ClosureStrategy`、`ClosurePlan` 各指一个阶段 | 证明语义改名为 `PlanProofRecord`，避免与物理闭合混用 |

## 4. 修订过程中发现的次生冲突

专家意见提供了冲突入口。沿端到端 fixture 继续推演后，本轮同时冻结以下派生决定：

| 次生冲突 | 架构裁决 | 直接影响 |
| --- | --- | --- |
| Diagnostic 同时保存事实、最终等级和有效性影响 | `DiagnosticRecord` 只保存 immutable 问题事实；`PolicyDecision` 独占最终 severity、disposition、validity effect 与 action payload | Exploration/Qualification 可以复用同一 record，策略演进不会改写事实 identity |
| RuntimeComponent、occurrence 与 cell identity 混用 | `ModelOccurrenceId` 标识 source/IR 放置；`RuntimeInstanceId` 是 plan-local slot；Runtime Cell identity 固定为 `(SessionId, RuntimeInstanceId)` | 多 Session 复用同一计划时不会伪造新 occurrence identity |
| RunBinding 示例携带或参与分配 RunId | `RunBinding` 只含 schema 允许值与 seed；Lifecycle allocator 为每次 attempt 分配 RunId，RunId 排除在 binding hash 外 | Experiment、reset、restore 的复现键与全局运行身份解除自引用 |
| InputFrameView 与 InputBundleView 未说明关系 | `InputFrameView` 是 Session 内部、随 transaction 失效的 slot 授权视图；Runtime Cell entry 将其投影为领域 typed `InputBundleView` | AlgorithmKernel 不接触 CycleFrame 布局，Session 仍可执行静态 handle 校验 |
| 诊断示例使用未登记 namespace | 调度失败使用 `GNC-SCH-0104`；`GNC.PLAN.*` 仅用于 proof assertion code | Diagnostic registry 与 proof registry 保持分域 |
| CompilationOutcome 状态与 plan 引用漂移 | 状态固定为 `Succeeded \| SucceededWithWarnings \| Failed`；成功结果发布 `PlanRef`，失败结果不发布可执行计划 | CLI、Python 与 Studio 使用同一结果 schema |
| RunManifest 未闭合 proof 交接 | manifest 必须保存 PlanProofIndex ref/hash，并与 source、plan、binding、package、build、commit、outcome 和 artifacts 同时登记 | 运行证据可以追到 Compiler 已证明的断言集合 |

这些决定已经同步进入 00A、04–08、10、12、14、glossary 与路线门，后续实现不得在语言 binding、日志 adapter 或 Session 内部另建平行语义。

## 5. 判定性完成标准

本轮修订完成需要同时满足：

1. 专家指出的三组跨册冲突在 glossary 有唯一裁决，07/08、05/06 正文一致；
2. 真实同义词的旧写法在专家原文之外归零；保留的近义对象在 glossary 写清阶段转换；
3. `PlanProofRecord` 有字段、断言类型、生成 pass、验证状态、consumer 和 YYZ 实例；
4. lineage edge 有数据结构、writer、commit 时机、存储位置和示例；
5. 09 的 Tool Adapter 部件可追到 DATCOM task，Task 状态可追到 Operation/Artifact 算子；
6. 05、07、08、09、10 各有可复制的数据实例，03–14 各有同一 fixture 的局部阅读入口；
7. 第一册可以只用核心词汇把 source、plan、run、CSV、Diagnostic、Artifact 与下一轮提案串成一条链；
8. README 规定术语注册、变更分级、实例依赖和能力状态治理；
9. R0 明确交付术语机器检查、旧行为 oracle 与 reference fixture conformance；
10. UTF-8、链接、Markdown、禁用句式和 `git diff --check` 审计通过。
